# 탑의 기록 외형 자동 관리

## 트리거
사용자가 "외형 이름 / 등급" 또는 이에 준하는 요청을 제공하면 실행한다. 별도의 이미지가 없다면 게임 기존 일러스트를 스타일 레퍼런스로 삼아 image generation 도구로 **새 이미지**를 생성한다. 도구가 이미지 파일을 제공하지 못하면 생성·배포 성공으로 보고하지 말고 파일 제공을 요청한다.

## 기준 저장소
- GitHub: `korgeek-sd/tower-chronicles`
- 카탈로그: `src/game/data/cosmetics.ts`의 `APPEARANCES`
- 이미지: `public/assets/characters/appearances/`
- 기존 이미지 변환 도구: `scripts/import-appearance.mjs`
- 기존 테스트: `tests/appearanceCatalog.test.ts`

## 입력과 등급
- 필수: 외형 이름, 등급
- 등급은 정확히 C, B, A, SR, SSR 중 하나. "일반/고급/희귀/영웅/전설"은 각각 C/B/A/SR/SSR로 해석하되 게임 내 실제 명칭이 다르면 사용자에게 확인한다.
- 외형 설명, 성별, 무기, 의상 등은 선택 사항. 지정하지 않으면 직업과 이름에 맞는 독창적인 다크 판타지 디자인을 생성한다.
- 사용자 제공 레퍼런스가 있으면 그것을 우선 사용한다.

## 처리 순서
1. 최신 기본 브랜치와 `cosmetics.ts`를 조회한다. 이름은 공백·대소문자·유니코드 정규화를 고려해 비교하고 ID도 검색한다. 중복 이름이나 애매한 일치는 사용자에게 확인한다.
2. 신규라면 고유한 ASCII snake_case ID를 생성하고, 기존 ID와 충돌하지 않는지 검증한다. 기존이면 원래 ID를 유지한다.
3. **스타일 일치 이미지 생성**: 전신 단일 캐릭터, 게임 기존 픽셀아트의 픽셀 밀도·비율·팔레트·명암·다크 판타지 분위기 유지, 검정 단색 배경 또는 투명 배경, 다른 캐릭터와 실루엣·장비 차별화. 기존 레퍼런스 이미지를 사용한다.
4. 생성된 이미지를 검수하고 1024×1024 투명 WebP로 변환한다. 픽셀아트에는 최근접 이웃 보간을 사용하고, 외곽 배경만 제거하여 검정색 장비나 윤곽이 훼손되지 않았는지 확인한다. SHA-256 앞 12자리로 `<id>-<hash>.webp` 파일명을 만든다.
5. 신규: `APPEARANCES`에 `id,name,rarity,imagePath,description,sourceLabel,tradeable,artStatus,proposedBonus` 등 기존 인터페이스에 맞는 항목을 추가한다. `proposedBonus`는 기존 `APPEARANCE_PROPOSED_PERCENT`를 참고하되 실제 전투 보너스를 활성화하지 않는다. 기존: `imagePath`만 변경하고 등급을 입력받았다면 기존 등급과 다를 때 확인을 요청한다. 기존 소유권, 컬렉션, 거래 및 밸런스 값은 보존한다.
6. 기존 `import-appearance.mjs`는 기존 ID의 imagePath만 교체할 수 있고 신규 카탈로그 등록을 지원하지 않는다. 신규에는 별도 카탈로그 수정이 필요하다. 이 스크립트는 Windows Chrome/Edge 실행 파일을 요구하므로 실행 환경을 먼저 확인한다. 스크립트의 기존 이미지 선삭제·직업 일러스트 자동 동기화는 안전성을 확인하지 않고 그대로 사용하지 않는다.
7. 최신 `main`에서 `skin/<id>-<짧은작업식별자>` 작업 브랜치를 먼저 만들고, 새 이미지와 해당 ID의 카탈로그 변경만 동일 변경 단위로 준비한다. 먼저 테스트 및 빌드 실행, 이미지 존재·참조 일치·중복 ID·등급·UI 노출 검증. 실패하면 배포하지 않고 기존 파일을 유지한다.
8. 검증 성공 시 `skin/*` 브랜치에 커밋/푸시하고 `main`을 대상으로 제목이 `skin-ready: <id>`로 시작하는 PR을 만든다 (`skin-ready` 레이블도 허용). `main`에 직접 푸시하거나 강제 푸시하지 않는다. 큐 워크플로가 변경 파일과 단일 외형의 메타데이터 보존, 이미지 해시, 병합된 테스트/빌드를 검증한 후 PR을 순서대로 병합한다. 충돌이면 배포 완료로 말하지 않고 해당 PR을 최신 `main` 기반으로 다시 작성해 재검증한다. GitHub 푸시만으로 실제 서비스 배포 성공을 단정하지 않는다. GitHub 푸시만으로 실제 서비스 배포 성공을 단정하지 않는다. Supabase가 관련된 데이터 소스라면 먼저 스키마와 권한을 확인하며 임의로 운영 테이블을 변경하지 않는다.
9. 보고: 이름, 등급, 신규/교체, ID, 이미지 경로, 작업 브랜치, PR, 테스트, `main` 병합 커밋, 배포 URL 및 실제 상태. 실행하지 않은 단계는 '미실행'으로 명시한다.

## 안전 원칙
- 기존 외형 교체 시 ID, 이용자 보유 데이터, 컬렉션 연결, 확률, 보너스, 직업 아트는 별도 요청 없이는 변경 금지.
- 운영 환경의 DB 데이터 변경, 인증정보 노출, 강제 푸시 금지.
- 기존 이미지 삭제는 배포 및 참조 검증 후 별도 정리한다. `scripts/import-appearance.mjs`가 구버전 에셋을 삭제하거나 직업 일러스트를 덮어써서는 안 된다.
- 이미지 생성·파일 저장·배포를 실제 수행하지 못했다면 완료했다고 말하지 않는다.

## 예시
- `심연의 기사 / SSR` → 조회 후 없으면 이미지 생성, 신규 등록, 검증, 배포
- `발키리 / A` → 기존 ID 확인, 새 이미지 생성, imagePath만 교체, 검증, 배포

## 배포 필수 완료 조건 (사용자 요청)
- 외형 이름·등급 또는 식별 가능한 기존 외형 이미지가 들어오면, **이미지 처리 → 작업 브랜치에 에셋 및 카탈로그 변경 → PR 제목 `skin-ready: <id>` → 자동 순차 병합 → Actions CI 확인 → GitHub Pages 배포 성공 검증 → 실서비스 이미지 URL 확인**까지 한 작업으로 진행한다.
- 사용자가 별도로 "배포해"라고 다시 말할 필요가 없다. 이미지 변환 파일 다운로드 링크만 제공하고 종료하지 않는다.
- 순수 이미지 교체는 기존 외형 ID/희귀도/소유 데이터/보너스/다른 직업 에셋을 변경하지 않는다. 파일명 해시 갱신으로 CDN 캐시를 무효화한다.
- `.github/workflows/ci.yml` 및 `.github/workflows/deploy-pages.yml`에서 해당 커밋의 테스트/빌드 및 배포 결과를 확인하고, **Pages 성공 후 서비스 자산 HTTP 200 및 이미지 파일 정상 여부까지 확인**해야 '배포 완료'라고 보고한다.
- CI 또는 Pages가 실패하면 원인과 실패한 단계, 수정 가능 여부를 확인하고 복구한다. 접근권한·배포환경 문제로 복구 불가능하면 배포 미완료로 명시한다.
- 일반적인 순수 에셋 작업에서는 버전·README·저장 스키마를 올리지 않는다. 기존 디자인이 제공된 경우 새로 생성하지 않고 그 이미지를 사용한다.

## 게임 UI 적용 확인 (필수)
- 동일 커밋의 `src/game/data/cosmetics.ts` 항목, `public/assets/characters/appearances/<id>-<hash>.webp`, 외형 목록의 `assetUrl` 경로를 확인한다.
- 실제 선택된 외형이 기본(default)이 아니라면 `playerGraphicForJob`은 착용 외형을 우선 표시해야 한다. 기본(default) 착용 시에만 직업 전용 일러스트를 표시한다.
- 외형 목록 이미지는 미보유 상태여도 표시하지만, 전투·사냥·거점에서 특정 외형을 보여주려면 사용자 계정이 해당 외형을 실제 보유·착용해야 한다. 소유권을 임의로 부여하지 않는다.
- Pages 배포 완료 이후 게임 화면 반영이 안 된다고 보고되면 빌드/배포 실행 이력, 서비스 JS 캐시, 캐릭터 이미지 선택 우선순위, 착용 상태 순서로 조사하고 재발 방지 테스트를 추가한다.

## 병렬 세션 안전 배포 규칙 (필수)
- 하나의 세션은 하나의 고유한 외형 ID만 수정한다. 각 세션에서 `skin/<id>-<작업식별자>` 브랜치를 새로 생성하고, 기존 브랜치를 다른 세션과 공유하지 않는다.
- PR 파일 변경은 `src/game/data/cosmetics.ts`의 정확히 한 외형 항목과 `public/assets/characters/appearances/<id>-<hash12>.webp` 신규 파일만 허용한다. 교체의 경우 `imagePath` 외 메타데이터 수정 불가. 신규 외형은 새 ID와 카탈로그 항목을 추가한다.
- 새 바이너리 이름의 해시는 실제 파일의 SHA-256 앞 12자리여야 한다. 이전 해시 파일과 다른 직업 에셋은 지우거나 변경하지 않는다. `git add -A`로 무관한 파일을 혼합하지 않는다.
- 작업 시작 때와 PR 제출 직전에 최신 `main`을 확인한다. GitHub 큐는 `.github/workflows/skin-pr-merge.yml`이며, `skin-ready:` 제목 또는 `skin-ready` 레이블이 있는 PR을 검증하고 직렬 병합한다. 서로 다른 ID의 변경이 같은 `cosmetics.ts` 위치에서 충돌하면 큐가 AST 기반으로 해당 ID만 최신 main에 재적용하여 PR 브랜치에 강제 푸시 없이 병합한다. 같은 ID가 서로 다르게 수정되었거나 다른 파일이 충돌하면 중단하고 사용자 선택을 요청한다.
- 레이블 이벤트가 중복되거나 대기 실행이 교체되어도 10분 간격 스케줄이 남은 PR을 다시 검사한다. 서로 다른 외형 ID 충돌은 자동 재적용을 시도하고, 동일 ID 충돌 또는 예상 밖 파일 충돌은 수동 검토가 필요하다.
- `main` 병합은 배포 완료가 아니다. 자동 병합이 사용하는 `GITHUB_TOKEN`으로는 일반 push-trigger 워크플로가 다시 실행되지 않으므로 큐가 CI와 Pages를 별도로 dispatch한다. 그 실행의 성공과 실제 이미지 URL까지 확인할 때만 배포 완료로 보고한다.
- GitHub 브랜치 보호 규칙 및 GitHub 네이티브 merge queue 활성화는 저장소 관리자 설정이며, 사용 가능한 API/권한이 없으면 활성화되었다고 보고하지 않는다. 관련 안내: `docs/skin-parallel-deployment.md`.
